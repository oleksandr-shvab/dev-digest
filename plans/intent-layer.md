# Development Plan: Intent Layer

## Requirement
"Derive the motivation ("intent") of a pull request from its title, its description, the linked issue or ticket, and any plan or specification the description links to, plus the list of changed files with their hunk headers. Store it per PR, pass it into the review together with the changes, show it on the PR page, let the user choose the cheap classifier model in Settings, and log what went into it.

Scope of the feature, six parts:
1. Intent classifier. A separate call to a cheap flash-class model through OpenRouter returns a structured intent: one sentence of intent, an in-scope list and an out-of-scope list. Input: PR title and description, linked issue/ticket, available plan or spec, and the list of changed files with hunk headers. Diff bodies are NOT sent.
2. Storage. The intent is stored for the specific PR. When the PR is updated, the user can run the derivation again.
3. Injection into the review. The structured intent is added to the reviewer's prompt. Comments outside the scope are filtered out, but a serious problem outside the PR's scope still leaves a signal.
4. Interface. The PR page shows an intent card before the review results, so the user can check that the system understood the task.
5. Model setting. The cheap classifier model is chosen separately from the main review model.
6. Observability. Log the prompt's components, the chosen model, the token estimate and the intent's sources, without secrets and without diff content.

Edge rules:
- Empty PR description → the classifier uses the title, file names and hunk headers, and the intent is marked with lower confidence.
- If the description references a ticket, a plan or a spec, those materials must be fetched and added to the intent's sources.
- A link that cannot be fetched is never silently replaced by invention: the stored intent must record the missing context."

Goal: one classifier call per PR (never on import, polling or page open) produces `{ intent, in_scope, out_of_scope }` from sources that are each recorded as used or unavailable; the result, its confidence and its sources are stored in `pr_intent`, shown in an `IntentCard` on the PR page, and injected into every review prompt. A deterministic gate then drops findings the reviewer marked `out_of_scope`, unless they are `CRITICAL` or the intent's confidence is `low`. The requirement arrived with decisions already made by the user (field name `intent`, source kinds, confidence function, add-only columns, two routes, pre-work behaviour, prompt slot, scope gate, placement, model default, UI, observability); the steps below implement them as given, and the ones that shape a contract are restated under `Contracts and data`.

## Out of scope
- Risk areas, blast radius, PR history and the PR brief score from the mock — other lessons.
- Any arbitrary outbound fetch (Jira, Linear, Notion, plain http). Such links are recorded as unavailable, never fetched.
- Fetching issues from a repository other than the PR's own. Such references are recorded as unavailable.
- Reading documents from the local clone, and any change to `GitClient` or `server/src/adapters/git/simple-git.ts`. Documents are read through the GitHub client.
- Calling the classifier from PR import, polling, or opening the PR page.
- Persisting `Finding.scope`, or showing a badge for it.
- Changing `reviewer-core/src/llm/openrouter.ts` (no `provider.require_parameters`): it would change every existing review call.
- Fixing `server/src/adapters/llm/pricing.ts` (it lists `z-ai/glm-4.7-flashx`, which is not in the OpenRouter catalogue, and outdated prices for `deepseek/deepseek-v4-flash` and `z-ai/glm-4.7-flash`). Pre-existing; reported under `For reviewers`.
- GitHub GraphQL `PullRequest.closingIssuesReferences` — possible follow-up; references are parsed from the description here.
- Using or changing `PrDetail.linked_issue` / `OctokitGitHubClient.resolveLinkedIssue`.
- Syncing the rest of `client/src/vendor/shared/adapters.ts` with the server copy (it already lacks `commitFiles`, `findOpenPr`, `sync` and `diffNameOnly`).
- Seeding a demo intent for PR #482, new e2e flows, and module `docs/` or `CLAUDE.md` updates (the `doc-writer` agent's job after implementation).
- Applying the migration to the developer's local database (`pnpm db:migrate` is the user's action).

## Call sequences
`POST /pulls/:id/intent` (derive or re-derive now):
1. `routes.ts`: `getContext(container, req)` → `workspaceId`; `IdParams` has already validated `:id`.
2. `ReviewService.deriveIntent`: workspace-scoped PR lookup (404), repo lookup (404), `loadDiff` (git diff, else the stored `pr_files` patches), then `IntentDeriver.derive` with a log built by `requestIntentLog(req.log, { prId })`.
3. `resolveFeatureModel(container, workspaceId, 'review_intent')` → provider and model (workspace override, else the registry default).
4. `container.llm(provider)` — fails here, before any fetch, when the key is missing. Log `Intent: deriving with …`.
5. `collectIntentSources`: `parsePrReferences` on the stored description (image embeds dropped; other-repository issues and external links recorded as unavailable without any request); when at least one own-repository issue or document is referenced, `container.github()` once, then in parallel `getIssue` on the PR's repository for up to three issues and `getFileAtCommit` at the PR's head sha for up to three document paths; `changedFilesOutline(diff)`. Every failure becomes an `unavailable` source with a fixed `detail` and collection continues.
6. Log one `Intent source:` line per source.
7. `intentConfidence(sources)`.
8. `buildIntentPrompt(materials)` → messages and component sizes.
9. `container.tokenizer.count` over all message contents → token estimate; log the `Intent prompt:` line.
10. Log `Intent: calling classifier…`, then `completeStructured` with the `Intent` schema, temperature 0 and the 4000-token output cap; a provider error becomes `ExternalServiceError`.
11. `clampIntent` on the returned data.
12. `ReviewRepository.upsertIntent` with the intent, confidence, sources, provider, model, the PR's head sha, tokens and cost → the stored row; log the `Intent derived —` line.
13. `intentRowToRecord(row, <PR head sha>)` → the response (`stale: false`).

Review pre-work (`POST /pulls/:id/review` → `ReviewService.runReview` → background `ReviewRunExecutor.executeRuns`):
1. The route returns the run ids at once, as today.
2. `executeRuns` builds the fanned-out `RunLogger` and loads the diff; a diff failure fails every run, as today.
3. `loadOrDeriveIntent` reads the stored row.
4. A row exists → it is used; logged as stored, or as stale when its head sha differs from the PR's. No classifier call.
5. No row → steps 3–12 of the sequence above, with every log line sent through `runLog.event`, so it reaches each run's Live Log, the persisted trace log and stdout.
6. Any error in 3–5 → one `info` line `Intent derivation failed — review continues without intent: …`; the intent is `undefined`.
7. For each agent: `runOneAgent` with the intent → `reviewPullRequest` → `assemblePrompt` renders `## PR intent (derived)` after `## PR description` (or nothing when there is no intent) → LLM → `reduceReviews` → `groundFindings` → the scope gate: skipped with one `info` event when the intent's confidence is `low`, otherwise `dropOutOfScopeFindings` with each drop emitted as an `info` event (not reached at all when there is no intent) → score from the surviving findings → persistence and trace as today (`prompt_assembly.intent` is in the trace).

## Risks
- PR text steering the scope lists to hide findings (the PR author controls the title, the description and the linked materials). Mitigations in this plan: the gate never drops a `CRITICAL` finding; it does not run at all when the intent's confidence is `low`; it acts on an enum value and a severity, never on intent text; every drop is an `info` event in the Live Log and the persisted trace; the intent is in an `<untrusted>` block with the governing rule outside it, and `INJECTION_GUARD` already says stated intent cannot turn a real defect into zero findings; the classifier has no tools and its system prompt forbids "ignore/skip/approve" scope items; the `IntentCard` shows the lists and their sources before the review results. Residual: a `WARNING` or `SUGGESTION` — including a security one — that the reviewer marks `out_of_scope` is dropped when the confidence is `medium` or `high` (see `Open questions`).
- An intent guessed from too little. With an empty description, or when every referenced material is unavailable, the confidence is `low` and the gate filters nothing: the intent is shown to the reviewer model as context only. This bounds the damage of an intent guessed from a title and file names alone — a wrong guess cannot remove a finding.
- Private issue text pulled in through a PR's references. With the user's GitHub token, a PR could otherwise name an issue of another (private) repository and have its text placed in the classifier prompt (sent to OpenRouter) and, summarised, in the review. Closed by the rule that only issues of the PR's own repository are fetched: an other-repository reference is recorded as unavailable and `getIssue` is always called on the PR's repository, never on an owner or name taken from the PR text; step 8's test asserts no call is made.
- Path traversal or symlinks when reading a referenced document. Mitigations: the parser rejects any path with `..`, `.`, empty segments or a backslash; `getFileAtCommit` validates the path again before any request; the file is read by GitHub from the PR's repository at the head sha, so nothing on the server's disk is opened; a response that is a directory listing, a symlink object or a submodule is refused; the reported size is checked before the content is decoded. Residual: GitHub's contents endpoint returns the target's content for a symlink that points to a regular file inside the same repository (as a `file` object), so such a link is read as its target; the content is still a file of the same repository at the PR's head commit, which the PR author can read anyway.
- The classifier model changing or disappearing on OpenRouter, or its routed provider not supporting structured output. The call then fails: the standalone route returns 502 and the review runs without intent with a logged reason; the model is one Settings change away (`google/gemini-3.1-flash-lite` is the researched alternative). The reasoning-capable default may spend output tokens on reasoning; the 4000-token cap leaves room, and a truncated answer fails schema validation and takes the same failure path. `require_parameters` is deliberately not sent.
- A stale intent after new commits. It is used as is in a review and logged as stale; `stale` is returned by the API and shown in the card with a "Re-derive" button. A review does not re-derive on its own, so a stale scope can mark newly added work as out of scope until the user re-derives.
- Cost of an extra call per review. The classifier runs once per PR, not once per review or per agent: later reviews reuse the stored row. At 0.042 / 0.084 USD per 1M tokens with capped inputs it is well under a cent. The cost is stored on `pr_intent`, not on an agent run, so the PR list's COST column does not include it. Two review triggers fired at the same moment for a PR with no stored intent can each make one call; the second upsert wins. A derivation also makes up to six GitHub requests (three issues, three documents), each with the adapter's own retry and 30-second timeout.
- Without a GitHub token no issue and no document can be read; they are recorded as unavailable and the confidence drops accordingly.
- Drift between the two vendored contract copies and the third registry mirror. Steps 1, 2 and 6 edit all copies in one step each; the `Done when` checks and the verification diff compare them; `pr-self-review` checks byte drift on touched vendored files. `adapters.ts` already differs between the copies, so that check will report a HIGH `vendor-drift` for it (see `Open questions`).
- Non-hermetic tests. Without step 10's change, the existing review integration suites would call OpenRouter and GitHub with the developer's real credentials on every run.
- The response schema sent to the reviewer model gains one nullable field (`scope`) for every review, including reviews with no intent; the messages are unchanged in that case.
- A secret in logs or stored rows through an error message. Source-fetch errors are mapped to fixed strings and their messages are never stored or logged; step 8's test asserts it.
